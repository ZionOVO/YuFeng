# 御锋 2.0 · 历史产品构想

> **非权威、不约束实现。** 本文只保留早期产品方向。当前架构见 [`architecture.md`](architecture.md)，网络行为见 [`api.md`](api.md)；仓库已经完成的软件能力、客户现场仍需提供的证据与条件型扩展，分别写在 [`delivery-evidence.md`](delivery-evidence.md) 和仓库根 [`implementation-plan.md`](../implementation-plan.md) 中。
>
> 定位（构想叙述）：漏洞从被发现到被真正修好之间有一段危险期（等官方补丁、等重启窗口）。御锋是**智能代理编排的修复系统**——用免重启的临时可逆修复填满危险期，同时把正式修复的报告与授权流程跑起来。
> 修复层级、自治等级和协议术语的完整含义见 [`glossary.md`](glossary.md)。

> **现行阅读校正**：智能代理编排不是让贾维斯订阅全量日志或直连边缘。数据面生产脱敏事件；原始流量只在 Edge 邻近 ModelSide 旁路内有界流转，Brain 仅接收类型化模型结果；中台唯一冻结检查票据和研判对象并按授权路由；贾维斯与调查执行实例消费不同投影，多站联动只走事件账与新资产世代。目标运行时是由持久线程、认知回合、步骤和有序记录组成的可恢复座架；技能、模型上下文协议桥、审批和委派都不能绕过工具白名单、对象绑定、租约、预算与副作用结算。正式语义见 [`architecture.md`](architecture.md) 第 4 至 5 节、[`api.md`](api.md) 第 18 与 21 节。

## 需求

1. **冷补丁**：感知资产被遗漏扫描或被人工智能驱动的渗透测试发现漏洞，结合开源情报、漏洞知识库和公开漏洞编号，由智能代理给业务直接打补丁——先出报告，等待用户授权。
2. **虚拟补丁 · 流量拦截**：用规则或受限的类规则手段拦截，也可用小模型检测抽样流量；智能代理不能审计全部实时流量。
3. **虚拟补丁 · 运行时约束**：用扩展 Berkeley Packet Filter 等机制约束系统调用或外部连接。

- 约束：流量拦截与运行时约束是不能要求业务重启的临时修复；三种修复皆由智能代理编排、分析和执行；被防御的设备资产多且异构。
- 场景三档：大型组织、小企业和家庭。

## 核心概念：修复连续谱

| 层 | 手段 | 表达域（能修什么） | 授权 |
|---|---|---|---|
| L0 | 报告 | 一切（不修） | 自动 |
| L1 | 虚拟补丁 · 流量拦截 | "请求形状"类漏洞 | 高危在野利用可短存活时限自动 |
| L2 | 虚拟补丁 · 运行时约束 | “系统调用行为”类（服务器端请求伪造外连、命令执行、数据外发） | 沙箱验证并以仅记录方式观察后自动 |
| L3 | 冷补丁（直接修复业务，可含重启） | 一切 | 永远人审 |

- 每层只表达漏洞行为的一个子空间；组合由策略角色决策。
- 虚拟补丁皆带存活时限，被冷补丁取代后自动退休——**虚拟补丁的生命周期管理本身就是产品**。
- 无官方补丁的设备（例如停止更新的摄像头和网络附加存储设备）：以流量拦截和运行时约束长期顶替，同样作为制品管理。

## 一个公开漏洞从发现到修复的生命线

情报摄入（已知被利用漏洞清单、漏洞利用预测评分和公开验证代码）→ 被动指纹匹配资产 → 沙箱用验证代码复现并提取利用行为签名（请求形状与系统调用序列）→ 策略角色产出分层修复计划 → 流量拦截制品经回放验证从只记录推进到全量生效 → 运行时约束从仅记录推进到全量生效 → 人工授权执行冷补丁 → 临时修复自动退休，审计链闭环。

## 智能代理驱动的三个闭环

1. **分钟级感知与响应**：研判角色值守事件流，可逆动作自动执行；
2. **天级学习与调优**：调优角色从流量画像差异提出检测器变更，经治理管道发布；
3. **持续攻防进化**：红队智能代理生成自适应攻击语料，评测面以固定基准衡量结果。

成本铁律：**贵模型发现，便宜模型拦截**——大模型只碰采样，发现蒸馏为微秒级同步制品。

## 三档场景

| | 域（大甲方） | 站（小企业） | 家（家庭） |
|---|---|---|---|
| 形态 | 分布式：分段边缘、资产侧执行集群与中台 | 单套容器编排与少量资产侧执行进程 | 路由器单二进制与云端中台 |
| 授权 | 基于角色的访问控制审批流 | 简化审批 | 可逆动作自动，冷补丁弹窗确认 |
| 红线 | 可完全离线部署 | — | **原始流量不出户**；误伤容忍极低（一个误伤=全家断网），设备画像包默认保守 |

## 历史构想摘录（曾按讨论纪要书写，不作为现行决定）

下列条目是构思阶段的设想，包括当时写过的「对象级基于角色的访问控制（RBAC）后置」。是否仍有效以 [`architecture.md`](architecture.md) 文末架构决策记录为准，本文不约束实现。

- 发布身份 = release_id + 全信封 artifact_id；治理、统计与边缘缓存以 release_id 为主键；
- 流量拦截层不设待审批状态：`PromoteCanary` 与 `PromoteEnforce` 是带门槛检查的执行命令，人工审批与对象级细粒度访问控制后置（历史构想，非本文现行决定）；
- 治理统计走心跳单调计数器，事件账只承载关键事件；
- 单元、资产与单元资产关系拆表，首版边缘先采用一单元对应一主资产；
- 首版操作域建立用户账户与管理员、操作员、查看者三个固定角色：支持登录、改密和管理员管理用户；对象级访问控制后置（历史构想，非本文现行决定）；
- 扩展 Berkeley Packet Filter 不设固定内核版本线：逐机探测能力，承诺口径为“运行时约束 · 手段自适应”；免重启手段仅限能够在线生效的内核机制，安全计算模式过滤与动态链接器预加载只适用于可重启场景；
- 冷补丁执行深度：引导式执行——授权后由平台执行，关键步骤人工确认；
- 首发场景：企业试点；家用形态只作演示。
